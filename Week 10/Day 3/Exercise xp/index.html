01

Understand JSON Web Tokens

A JWT is a compact, signed way to carry claims between a client and a server.

A signed JWT commonly has three Base64URL-encoded parts separated by dots: header.payload.signature. The header names the signing algorithm, the payload contains claims such as a user ID and expiry, and the signature lets the server detect tampering. Signing does not encrypt the payload: never put passwords, secrets, or sensitive personal data in it.

Authentication vs. authorization: authentication establishes who the user is; authorization checks whether that user may perform a particular action. A valid token alone does not grant every permission.
02

Set up a Node.js and Express app

Create a small API project and start with one health-check route.

mkdir jwt-auth-api
cd jwt-auth-api
npm init -y
npm pkg set type=module
npm install express jsonwebtoken bcrypt cookie-parser
npm install --save-dev nodemon
mkdir src
# Create src/server.js

Add a development script with npm pkg set "scripts.dev=nodemon src/server.js". In src/server.js, create the Express app, enable JSON request bodies with express.json(), and listen on a local port.

Note: Modern Express includes JSON body parsing. You do not need the separate body-parser package for express.json().
03

Know the dependencies

Each package has a specific job in this example.

  • express creates the HTTP server and routes.
  • jsonwebtoken signs and verifies JWTs.
  • bcrypt hashes passwords and compares login attempts.
  • cookie-parser reads cookies from incoming requests.
  • express.json() parses JSON bodies; no extra body-parser package is needed.
04

Model users and hash passwords

Registration should validate input and store only a password hash.

For the first exercise, use an array of user objects with a unique ID, normalized email, and passwordHash. Check for duplicate email addresses. Use bcrypt.hash(password, 12) before saving; on login, use bcrypt.compare(password, user.passwordHash). Never save or log the submitted password. Replace the array with a database for real applications.

05

Issue short-lived access tokens

Registration and login can return an access token after credentials are verified.

Keep the signing secret in an environment variable, not in source control. Create a strong random secret (at least 32 random bytes) for local development. Sign only the minimum claims needed, such as the user ID in sub, and set an expiry: 

const accessToken = jwt.sign(
  {},
  process.env.JWT_ACCESS_SECRET,
  { subject: user.id, expiresIn: '15m', algorithm: 'HS256' }
);

Use different secrets for access and refresh tokens. In production, validate that required secrets are configured at startup and fail explicitly if they are missing. Do not use a placeholder or a default secret.

06

Verify tokens in authentication middleware

Read the access token, verify its signature and expiry, and attach its subject to the request.

function authenticate(req, res, next) {
  const header = req.headers.authorization;
  const [scheme, token] = header?.split(' ') ?? [];

  if (scheme !== 'Bearer' || !token) {
    return res.status(401).json({ error: 'Authentication required' });
  }

  let claims;
  try {
    claims = jwt.verify(token, process.env.JWT_ACCESS_SECRET, {
      algorithms: ['HS256'],
    });
  } catch {
    return res.status(401).json({ error: 'Invalid or expired token' });
  }

  if (typeof claims === 'string' || typeof claims.sub !== 'string') {
    return res.status(401).json({ error: 'Invalid token claims' });
  }

  req.userId = claims.sub;
  next();
}

Verification must use the expected secret and an explicit allowed algorithm. Treat the decoded claims as untrusted input until verification succeeds. Return 401 when authentication is absent or invalid; do not leak signature, secret, or token details in the response.

07

Protect routes and check permissions

Attach authentication middleware only to routes that require a signed-in user.

app.get('/api/profile', authenticate, async (req, res) => {
  const user = await findUserById(req.userId);
  if (!user) return res.status(404).json({ error: 'User not found' });

  res.json({ id: user.id, email: user.email });
});

Do not return password hashes. For a user modifying their own profile, derive the account ID from verified claims instead of trusting a user ID supplied in the body. For roles or other permissions, add explicit server-side authorization checks and return 403 when an authenticated user is not allowed to act.

08

Store tokens in HTTP-only cookies

Cookies can keep tokens out of JavaScript, but cookie-based auth needs CSRF protection.

When setting a token cookie, use httpOnly: true, secure: true in production over HTTPS, an appropriate sameSite setting, a narrow path, and a short maxAge. Use cookie-parser to read it. If your app sends cookies cross-site, configure CORS credentials carefully and add CSRF defenses; SameSite is not a complete substitute in every setup.

A logout route should clear the cookie using the same path and relevant options used when setting it. Clearing a cookie in the browser does not, by itself, invalidate a copied JWT; short access-token lifetimes and server-side refresh-token revocation help address that gap.

Choose storage deliberately: do not put long-lived tokens in localStorage. HTTP-only cookies reduce exposure to token theft through injected JavaScript, but require CSRF-aware cookie and request handling.
09

Add refresh tokens with rotation

Refresh tokens extend a session without making access tokens long-lived.

  1. LoginIssue a short-lived access token and a longer-lived refresh token.
  2. StorePut the refresh token in a secure, HTTP-only cookie.
  3. RefreshVerify it, check server-side session state, then issue a new pair.
  4. RotateRevoke the old refresh token when the new one is issued.

Store a hash or identifier for each refresh token in a database, along with its user, expiry, and revocation status. On /refresh, verify the token, confirm it is still active, revoke it, and issue a replacement. If a revoked token is reused, revoke that session's token family and require a new login. The /logout route should revoke the active refresh token and clear its cookie.

Never trust a refresh cookie alone: verify its signature, expiry, intended token type, and active server-side session before issuing another access token.
XP

Build it, then extend it

Turn the guide into a working authentication API with clear success and error responses.

Core requirements

  • Create POST /register and POST /login with validation and bcrypt password hashing.
  • Issue signed, expiring access tokens and protect GET /profile with authentication middleware.
  • Use an HTTP-only cookie for the refresh token; implement POST /refresh and POST /logout.
  • Use environment variables for secrets, and return appropriate 400, 401, 403, and 409 responses.

XP extensions

  • Enforce username and password rules, and let an authenticated user update their own profile.
  • Replace in-memory users with persistent database storage.
  • Add email confirmation with one-time, expiring tokens.
  • Rate-limit login and refresh endpoints to slow brute-force attempts.
  • Test expired, malformed, revoked, and replayed refresh tokens, plus unauthenticated and unauthorized requests.
Before calling it done: confirm a wrong password never logs in, an expired or altered access token gets 401, a forbidden action gets 403, logout revokes the refresh session, and secrets never appear in responses or version control.
JWTs are one part of an authentication system. Keep dependencies updated, use HTTPS, validate inputs, and follow the current security guidance for your framework and deployment.
